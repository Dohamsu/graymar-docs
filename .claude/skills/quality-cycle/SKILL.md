# 품질 사이클 — 런 → 분석 → 수정 → 재검증

게이트 15종은 계약 위반을 잡지만, "말이 되는가"(단서 이해 가능성·톤 다양성·
서술 중복)는 **전문 정독**으로만 잡힌다 (arch/104·105가 이 방식으로 발굴됨).
이 스킬은 2026-09-01 세션에서 실증된 사이클의 정본이다 — 그 세션의 산출:
fact 키워드 충돌 4건(버그 8db24757)·셸 턴 출발 재서술·단서 경고 톤 수렴.

## 모드

- **기본 (full)**: 4단계 전부. 수정은 신규 결함만, 커밋은 하지 않는다.
- **report-only**: 1~2단계 + 수정 제안까지만. `/loop` 연계 시 이 모드만 사용
  (자동 루프에서 코드·콘텐츠를 승인 없이 고치지 않는다).

## 1단계 — 테스트런

```bash
cd /Users/dohamsu/Workspace/graymar   # 반드시 레포 루트
python3 scripts/playtest.py --turns 10 --agent chatty \
  --scenario <팩ID> --preset <프리셋ID> \
  --output playtest-reports/run_$(date +%Y%m%d)_qc.json
```

- 10~15턴 기본 (롱런 금지 — CLAUDE.md 플레이테스트 규칙). 페르소나는 점검
  목적별 선택 (대화·단서=chatty, 압박=coercer, 재해석=weirdo).
- 팩은 로테이션 — 직전 사이클과 다른 팩 우선.
- 백그라운드 실행 시 `| tail` 파이프 금지 (출력 버퍼링으로 중간 확인 불가).

## 2단계 — 분석 (게이트 + 정독)

**게이트**: 15/15 확인. 단일 런 게이트(V9 등)의 FAIL 은 직전 2~3런과 대조해
노이즈 여부 판단 — 1런 표본은 1건이 5%p다 (arch/79 §11.3).

**정독 (핵심)**: run_id 로 DB 에서 전 턴을 꺼내 **전문을 읽는다**:

```sql
SELECT turn_no, llm_output FROM turns WHERE run_id='<ID>' ORDER BY turn_no;
-- 보조 계측:
--   server_result->'ui'->'questReveal'  (fact 공개 기록·모드)
--   llm_speech_audit                    (어체 위반, 서버가 이미 기록)
--   llm_npc_reaction                    (nano 사전결정 — refusalLevel 분포)
--   llm_token_stats->'promptChars'      (예산 밴드)
```

정독 체크리스트 (실증된 발굴 축):
1. **단서 이해 가능성** — questReveal 턴의 발화가 그 시점 플레이어의 선행
   지식으로 이해되는가. 미조우 개체 지시어("그 귀환자")·종반부 fact 조기
   발화 의심 시 fact 의 stage·keywords·보유자 표시명 충돌을 대조.
2. **질문-답 정합** — 물은 것과 답이 잇닿는가. rumor(stale 자동 발견)는
   타이밍 어긋남이 알려진 잔여 특성.
3. **톤 분포** — 단서 전달이 경고 일색인가(거부·조심하라·다친다). nano
   refusalLevel 분포로 수치 확인 (POLITE 쏠림 = arch 진단 재발).
4. **전환·반복** — 이동↔셸 턴 비트 중복, 연속 턴 마감 비트 재사용, 문구
   단위 에코.
5. **인물 정합** — 화자의 장소(스케줄 대조)·어체(speech_audit)·마커·
   즉흥 무명 인물 등장.
6. **스토리 인과** — FAIL 판정이 서사 장애물로 번역되는가, NPC 미니 아크
   성립 여부, 미회수 스레드.

**분류 규칙 (중요)**: 발견 항목마다 먼저 **기존 등재 트랙 귀속**을 시도한다
(arch 문서·CLAUDE.md 잔여 목록 — npcLocations desync, 되묻기, 반복 억제,
어체 잔존율 등). 기존 계열이면 "재확인"으로 기록하고 수정하지 않는다.
신규 트랙 남발이 이 사이클의 최대 실패 모드다.

## 3단계 — 수정 (신규 결함만, full 모드 한정)

- **근본 원인 먼저**: 콘텐츠 → nano → 프롬프트 → 서술의 인과 사슬에서
  최상류를 찾는다. 서술 증상을 프롬프트 규칙 추가로 덮지 않는다 (LLM 대응
  원칙 6 — 데이터·서버 로직 우선).
- 콘텐츠 수정 시: 불변식 42(어구 예시 금지)·50(구체 어휘 앵커) 준수,
  `python3 scripts/audit_content.py` 통과 필수. 재발 방지가 가능하면 감사
  규칙을 정본에 추가한다 (FACT_KEYWORD_HOLDER_COLLISION 이 선례).
- 프롬프트 수정 시: 골든 스냅샷 갱신 후 diff 가 의도 변경뿐인지 검토.
- 서버 코드면 `pnpm build` + 전체 테스트.
- **커밋 금지** — 수정·검증 결과를 보고하고 커밋은 명시 요청을 기다린다.

## 4단계 — 재검증 (표적 프로브 우선)

전체 런 재실행은 최후 수단이다 — **일반 런은 CORE 우선 배정 때문에 검증
대상 NPC·경로를 안 지나갈 수 있다** (실측: 12턴 검증 런이 수정 NPC 0명
조우). 대신:

1. **재현 프로브**: 결함 시나리오와 동일한 입력을 스크래치 스크립트로 직접
   제출 (로그인 `playtest@test.com`/`Test1234!!` → 런 생성 → 지목 ACTION →
   `questReveal`·서술 대조). 명시 지목은 화자 결정 1순위(불변식 34)라
   대상 NPC 를 확정적으로 소환한다.
2. 프로브 스크립트는 스크래치패드에만 — scripts/ 에 새 정본을 만들지 않는다.
3. 콘텐츠 변경은 서버 재기동 후에만 반영된다:
   `launchctl kickstart -k "gui/$(id -u)/com.graymar.server"`.

## 보고 형식

증상 → 결정적 근거(원문 인용) → 근본 원인 → 조치(수정 완료 / 기존 트랙
재확인 / 신규 제안) 표. 수정했으면 재검증 결과 포함. 미커밋 파일 목록 명시.

## 루프 연계

`/loop /quality-cycle report-only` 로 주기 실행 가능하나, 런당 LLM 비용
(~수십 원)과 분석 토큰이 들므로 상시 루프보다 **배포 후·콘텐츠 추가 후
수동 1회**가 기본이다.
