# 139. Dimtale 기억 방식의 Graymar 이식 — 원문 회상 블록

> 상태: R1·R2 구현·배포(2026-10-12), R4 오프라인 재생 1차 완료(§6). R3·V15 게이트는 미착수.
> 참고: `../dimtale/design/17_memory_first_engine.md`, `50_memory_stability_and_recall.md`, `55_grounded_request_and_evidence_retrieval.md`

## 0. 결론

Dimtale의 엔진 전체(장면 모델이 성공·시간·세계 변경까지 판단)는 가져오지 않는다. 불변식 1·2(서버 정본, LLM 서술 전용)와 충돌하고, 스트리밍 산문 출력도 버려야 하기 때문이다.

가져올 것은 하나다. **"확정된 턴 원문을 버리지 않고, 이번 플레이어 입력을 검색어 삼아 과거 원문을 통째로 다시 보여 준다."**

Graymar에는 이미 재료가 있다. `turns.raw_input`과 `turns.llm_output`이 턴마다 변경 없이 남아 있다. 지금은 이 원문을 최근 몇 턴(locationSessionTurns, 거리별 300→100자 절삭)과 요약본(midSummary 200자·summaryShort 60자·entity_facts UPSERT)으로만 쓴다. 검색 경로만 없다. 새 저장소 없이 **읽기 경로 하나**로 시작할 수 있다.

## 1. 왜 Graymar에서 회상이 약한가 (원인 4)

| 원인 | Graymar 현재 | Dimtale |
|---|---|---|
| 저장 시 손실 | 요약 저장(60자·200자), v4 사실 UPSERT가 같은 key를 최신 값으로 **덮어씀**, 주입 시 nano가 다시 요약 | 원문 불변 보존, 파생 자료는 원문 구절을 가리킴 |
| 꺼내는 기준 | 엔티티 존재(등장 NPC·현재 장소, 불변식 24) | 이번 입력이 검색어 |
| 프롬프트 몫 | 메모리 2,500 tok 중 구조화 기억 450 tok, 나머지는 지시 블록 | 입력의 중심이 기억 원문 묶음 |
| 정본 | 서버 상태 — 대화 속 약속·별명 같은 비정의 세부는 정본에 없음 | 확정 장면 원문 자체가 기록 |

## 2. 이식 범위

### R1. 회상 블록 `[과거 장면 원문]` (읽기 전용, 저장소 변경 0)

- **후보**: 같은 런의 `llm_status=DONE` 턴 중 `[이번 방문 대화]` 창 밖의 턴 전부. 런이 10~40턴이라 전수 스캔으로 충분하다(Dimtale이 미해결로 남긴 장기 확장성 문제가 Graymar에는 없다).
- **단위 = 한 턴 묶음**: 플레이어 입력 + 그 턴의 NPC 대사(마커 npcId로 화자 확정) + 서술 앞뒤 문장. **대사는 자르지 않는다.** 예산이 모자라면 묶음 수를 줄인다(Dimtale 50 §조회 5).
- **매칭**: 서버 결정론. 조사 제거 후 음절 bigram 겹침 + 화자 일치(현재 대화 상대 = 과거 화자) + 기존 `extractFactQueryKeywords` 재사용. 새 LLM 호출은 넣지 않는다.
- **발화 게이트 (불변식 50 대응)**: 원문 대사를 넣으면 그대로 낭독될 위험이 있다. 1차는 **회상 신호가 있는 입력에만** 켠다(아까·전에·그때·약속·뭐라고 했·기억 등 + 과거형 질문). 상시 주입은 R4 계측 후에만 검토한다.
- **예산**: 최대 2묶음·약 800 tok. 메모리 블록 예산 안에서 배정하고, 백스톱 제거 순서에서 기억과 같은 보호 등급을 준다.
- **위생**: 미소개 실명은 `maskHiddenNpcNames` 정본으로 처리한다(불변식 51). 마커는 표시명으로 풀고, 원문은 이미 플레이어에게 노출된 텍스트이므로 미발견 fact 누출 위험이 없다.
- **지시문**: 완성 예시 문장 없이 구성 요소만 쓴다(arch/105 P0-3). "아래는 실제로 오간 원문이다. 과거를 언급할 때 이와 어긋나지 말라."
- **배치**: `context-builder.service.ts`에서 조립하고, arch/114 T2 블록 레지스트리에 등록한다. `[이번 방문 대화]`와 같은 턴이 겹치지 않는지 배타 검사를 추가한다.

### R2. NPC 관점 범위

NPC가 응답할 때는 **그 NPC가 있었던 턴만** 후보로 쓴다(과거 화자였거나 primaryNpcId였던 턴). Dimtale의 "캐릭터가 실제로 접한 것만" 원칙이다. 이 범위가 없으면 A에게 한 말을 B가 아는 지식 혼선이 생긴다.

### R3. 쓰기 손실 줄이기 (후순위)

- entity_facts UPSERT를 **append + sourceTurnNo**로 바꿔 이력을 남기고, 최신 값은 조회 시 계산한다.
- NpcPersonalMemory 항목에 `sourceTurnNo`를 붙여 요약에서 원문으로 되짚어 갈 수 있게 한다.

### R4. 단계 분리 계측 (R1과 동시 착수)

Dimtale이 결함을 찾은 방식이다. 하나의 회상을 아래 단계로 나눠 각각 센다. "검색 성공"을 "기억 성공"으로 보고하지 않는다.

1. 원문 존재 → 2. 후보 검색 적중 → 3. 예산 안 주입 → 4. 서술에서 실제 사용(핵심 구절 일치) → 5. 오용(엉뚱한 과거 인용·낭독)

- 고정 사례: 실런에서 T(n)의 약속·별명·물건을 T(n+5)에 되묻는 입력을 만들어, 회상 블록 OFF/ON을 같은 프롬프트로 재생 비교한다.
- playtest 게이트 V15(회상 근거 포함률·사용률·낭독률)를 추가한다 — V14 는 NPC 대화 게이트(arch/104)가 이미 사용. 에이전트 페르소나에 "과거 되묻기" 행동을 넣는다.

## 3. 가져오지 않는 것

- 장면 모델의 세계 판정·JSON 구조 출력 — 불변식 1·2, 스트리밍(arch/35)과 충돌한다.
- 턴마다 비동기 Luna 보존 분류 — 런이 짧아 보존 등급이 필요 없고, 호출 비용만 두 배가 된다.
- 형태소 분석기(kiwipiepy) — Node 서버에 Python 의존성이 생긴다. bigram + 기존 키워드 매처로 시작하고, R4에서 적중률이 부족하다고 확인될 때만 재검토한다.

## 4. 순서와 완료 조건

1. R4 고정 사례 세트와 OFF 기준선 측정
2. R1 구현(회상 신호 게이트) + R2 범위 + 스펙(매칭·마스킹·예산·배타)
3. 같은 사례 ON 재생 → 사용률 상승, 낭독률·오용률 비악화 확인
4. 두 팩 10~15턴 실런 2회, V15 기록
5. 결과에 따라 게이트 확대(상시 주입) 또는 R3 착수

완료 조건: 되묻기 사례에서 OFF 대비 사용률이 오르고, 일반 턴의 낭독·반복 지표(V9)가 악화되지 않을 것. 표본이 작으면 "개선 확인"이 아니라 "신호"로 보고한다.

## 5. 모델 변경과의 관계

같은 날 메인 서술을 GPT-6 Luna 단일 모델로 바꿨다(교차 없음, 추론 none). 모델이 바뀌면 긴 맥락 주의력도 함께 바뀐다. 그래서 R4 기준선은 **모델 전환 후** 측정해야 한다. 그래야 회상 블록의 효과와 모델 효과가 섞이지 않는다.

## 6. 1차 구현과 측정 (2026-10-12)

### 6.1 구현

- `server/src/llm/recall-block.core.ts`(+스펙 13): 회상 신호 → 같은 런 과거 턴 묶음 선택 → `[과거 장면 원문]` 렌더. `context-builder.buildRecallContext` 가 신호 있는 턴에만 DB 를 조회하고(평소 턴 쿼리 0), `sanitizeNpcNames`(정본 `maskHiddenNpcNames`)로 마스킹한다. 기억 블록 우선순위는 HIGH(`[이번 방문 대화]`와 같은 등급).
- 골든 스냅샷 17건 불변 — 회상 신호가 없는 턴의 프롬프트는 바이트 단위로 같다.

설계 대비 바뀐 점 3가지. 모두 실측으로 드러났다.

1. **서술 문장도 싣는다.** 1차는 대사와 플레이어 입력만 실었다. 그런데 쪽지에 적힌 낱말은 서술에만 있었고, 모델은 없는 낱말('소행이')을 지어냈다(run ba2b5741 T18). 그래서 검색어 2개 이상이 닿는 문장과 그 바로 다음 문장을 싣는다. 묶음당 최대 3문장이며, 문장은 자르지 않는다.
2. **회상 질문 턴은 근거에서 뺀다.** 지어낸 대답이 다시 근거로 쓰여 원문을 이겼다(T20: T5 원문과 T18 오답이 함께 주입되자 모델이 오답을 따름). 자기강화 고리를 끊는 조치다.
3. **충돌 지시를 끈다.** 회상 턴에 `[이미 나눈 대화·전한 정보 — 반복 금지]`의 "재언급 금지"와 `[NPC 빈손 — 인계 가이드]`의 "모른다고 인정"이 함께 실려, 원문을 받고도 "모르오"로 빠졌다. 회상 턴은 기존 재질문 변형(`재질문 외 반복 금지`)을 타게 하고, 빈손 가드는 끈다. 두 빈손 블록은 레지스트리에 미등록 상태였어서 이번에 등록했다. 회상 블록은 memoryParts에 있어 레지스트리의 공존 금지 쌍 검사(factsParts 전용)로는 잡을 수 없으므로 코드 게이트로 차단한다.

### 6.2 R4 오프라인 재생 (GPT-6 Luna, 같은 프롬프트에서 블록만 넣고 뺌, 각 5회)

| 사례 | OFF | ON (블록만) | ON + 충돌 지시 정리 |
|---|---|---|---|
| Q1 대사 회상 — 회계사가 요구한 조건(T7 "믿을 만한 줄을 하나 대시오") | 0/5 (조건 부정·지어냄) | 2/5 | **5/5** |
| Q2 서술 회상 — 쪽지 낱말(T5 서술 '경비대 지구'·'조작'·'내부') | 0/5 (5회 모두 지어낸 낱말) | **5/5** | — |

정답 10회 모두 원문을 그대로 낭독하지 않고 인물의 말투로 다시 말했다. **한계**: 한 런의 사례 2개이고 같은 프롬프트 반복이라 독립 표본이 아니다. "개선 확인"이 아니라 강한 신호로 기록한다.

### 6.3 발화 빈도 (최근 45일 ACTION 1,253건)

회상 신호가 잡힌 입력은 80건(6.4%)이다. 무작위 25건 중 24건이 실제 되묻기였고, 1건("아까 손가락에 묻은 먼지가… 닦아드릴까요?")은 오탐이지만 해가 없다. 같은 되묻기("이렌, 아까 창고 얘기를 했는데 그게 정확히 어디죠?")가 한 런에서 6회 이상 반복된 기록이 있다. 대답이 원문을 받지 못해 플레이어가 계속 되물었던 흔적으로 보인다.

### 6.4 남은 일

- V15 플레이테스트 게이트: 에이전트 페르소나에 되묻기 행동을 넣고, 주입률·사용률·낭독률을 런 단위로 누적한다.
- 같은 런 안에 이미 오염된 대답(T18·T20의 '소행이')은 [이번 방문 대화]의 THREAD 요약에 남는다. 회상 블록만으로는 지울 수 없어, 회계사는 T21에서 "이미 말했소"로 회피했다. 지시문에 "원문과 이전 대답이 다르면 원문을 따른다"를 넣을지는 V15 표본을 본 뒤 정한다.
- R3(쓰기 손실 축소)는 미착수.
- 판정 문제: 회상 질문이 PERSUADE PARTIAL("핵심은 숨겨짐")로 판정됐다. 지난 대화를 되묻는 것이 주사위 판정 대상인지는 ChallengeClassifier 쪽 별도 검토가 필요하다.

## 7. 기억 계층 실측 점검 (2026-10-12, 배포 후)

### 7.1 회상 블록 — 오염 없는 새 런 실플레이 (run 159d5b40)

시장에서 대화한 뒤 선술집에 다녀오고(장소 전환 2회, 8~10턴 경과) 회계사에게 한 번씩만 물었다.

| 질문 | 원문 | 대답 |
|---|---|---|
| T14 "지난밤 일을 물었을 때 누가 무엇을 했다고 했었소?" | T4 대사 "기록을 들춰 보던 이들이 있었단 말은 들었소" | "기록을 살핀 이들이 있었다는 얘기였소" ✅ |
| T15 "좌판 아래 찢긴 종잇조각에 적힌 글자를 기억하시오?" | T5 서술 '경비대 지구', '내부' | "'경비대 지구'와 '내부'였소" ✅ |

신호가 없는 턴(T8~T13)에는 블록이 실리지 않았다.

### 7.2 기존 기억 계층에서 확인한 결함 (모델과 무관, 미수정)

1. **THREAD 요약은 사실상 한 번도 작동하지 않았다.** `llm-worker` 의 THREAD 생성(태그 파싱 → 대체 요약 → nano 요약 → `node_memories.narrative_thread` 저장)이 `if (!jsonModeParsed && !isStreamingMode)` 블록 안에 있다. 스트리밍이 기본값(arch/35)이 된 뒤로는 비스트리밍 대체 턴에서만 돈다. 최근 150일 노드 약 1,100개 중 thread 가 저장된 노드는 3개다. 그래서 `[이번 방문 대화]`는 "THREAD 요약 사용(원문 주입 폐기)"이라는 주석과 달리 매 턴 **원문 끝 60자** 대체본을 싣고 있다.
2. **entity_facts(기억 v4) 커버리지와 품질.** LOCATION 턴 중 사실이 저장되는 비율은 약 30%로, 모델과 무관하게 주차별로 일정하다. fire-and-forget 이라 실패 원인은 남지 않는다. 저장된 사실의 상당수는 몸짓·목소리 묘사("호흡: 빠른 숨")다. 지어낸 회상 대답도 사실로 저장된다(run ba2b5741: "기억_빈칸: '소행이'라는 말만 기억"). 소비 블록 `[기억된 사실]`은 LOW 우선순위라 예산 압박 시 가장 먼저 잘린다.
3. **R2 범위의 한계.** 대화 상대가 그 턴의 화자나 대화 상대였어야 후보가 된다. 같은 장면에서 곁에 있었던 NPC가 들은 말은 회상하지 못한다(예: T7 실무자 발언을 회계사에게 물으면 후보 0). 그 턴의 NPC 동석 정보를 저장하지 않기 때문이다.
