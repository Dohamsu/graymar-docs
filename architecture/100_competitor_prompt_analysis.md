# 100. 경쟁 텍스트게임 프롬프트 구조 분석 — 서술 기법 이식 검토 (2026-08-12)

> **상태**: 📎 분석 완료 · 실행 항목 5건 중 2건 착수 가능, 2건 소유자 결정 대기, 1건 기각 권고
> **자료 출처**: 소유자 제공 스크린샷 4장 (`천하만리행` / 플랫폼 `프로챗 1.0`).
>   **원문 시스템 프롬프트가 아니라 모델의 thinking(CoT) 노출분**이며, 모델이 자기
>   규칙을 점검하는 과정에서 규칙 구조가 역으로 드러난 것을 재구성했다.
> **범위**: 프롬프트 아키텍처와 서술 기법만. 예시 장면의 콘텐츠(성적 비동의 묘사)는
>   분석 대상에서 제외했다.

## 1. 자료의 성격과 신뢰도

화면에 노출된 것은 사고 트레이스이고, 마지막 줄에
`[//]: # (Never describe the PC's actions, dialogues, or feelings predictively.)`
가 리터럴로 찍혀 있다. 두 가지가 확인된다.

- 그쪽 시스템 프롬프트는 **마크다운 주석(`[//]: #`)으로 규칙을 은닉**한다.
- 그 규칙이 **출력에 새고 있다** — 프롬프트 유출. 우리 `V7_no_leak` 게이트가
  잡는 부류의 결함이 상시 노출되고 있다.
- 사고는 **영어**, 출력은 한국어다 (한국어 게임인데 CoT는 영어).

따라서 아래 "규칙"은 원문 인용이 아니라 **CoT 자가점검 항목에서 역추론한 것**이다.
구조는 신뢰할 만하나 문면은 추정이다.

## 2. 사고 파이프라인 (5단계 고정)

모델이 스스로 번호를 매겨 진행한다.

| 단계 | 내용 |
|---|---|
| 1 | 유저 의도 파악 |
| 2 | **Character Analysis** — `Previous State` / `Current State` / `Reaction to PC's words` |
| 3 | **Scene Setting** — `Atmosphere` |
| 4 | **Drafting** — POV 명시(3인칭 제한) → `Opening` / `Internal Monologue` / `Physical Description` |
| 5 | **Review and Refine** — `Check Rules` / `Tone·Style` / `Dialogue Weight` |

2단계가 특징적이다. 캐릭터를 "현재 어떠하다"가 아니라 **"이전 → 현재의 변화량"**
으로 파악한다. 그래서 묘사가 상태 서술이 아니라 **델타 서술**로 나온다.

## 3. 상황묘사 기법 5종

### 3.1 장면마다 "핵심 대비" 한 쌍을 먼저 확정
CoT에 `The contrast between A and B is key` / `contrasts sharply with` /
`psychological whiplash` 가 반복된다. 감각을 나열하지 않고 **대비축을 먼저 정한 뒤
모든 묘사를 그 축 보강에 배치**한다.

### 3.2 Atmosphere를 감각 채널로 분해
후각 → 시각(조명) → 촉각/신체 상태를 각각 슬롯으로 채운다. "분위기" 한 덩어리가
아니다.

### 3.3 문단 구성을 순서로 고정
`Opening(물리 감각) → Internal Monologue(심리) → Physical Description(신체)`.

### 3.4 심리 전개를 단계로 분해 — **이 게임 서술 품질의 핵심 장치**
`Internal Monologue` 하위가 5스텝으로 쪼개진다:
① 외부 자극 수신 → ② 의미 처리 → ③ 1차 감정 → ④ 회상 → ⑤ 혼란으로 착지.
한 문단 안의 심리 흐름을 설계하고 들어간다.

### 3.5 대사는 짧게, 무게는 독백이 담당
`Dialogue Weight` 규칙 — 최종 발화는 짧되 무겁게, 분량은 내적 독백이 진다.

## 4. 역추론된 규칙 목록

| 규칙 | 내용 |
|---|---|
| PC control | PC 행동·대사·감정 예측 서술 금지. 응답은 NPC 반응만 |
| **Narrator quotes** | PC 대사를 나레이션에서 직접 인용 금지 → 감각 표현으로 전환 |
| Image | 캐릭터 폴더 + 번호 파일(`유은설/46.webp`), 감정 태그로 매칭 |
| INFO Block | 시간 갱신 |
| UI Block | 호감도(이모지 척도), 상태(아이콘+수치) |
| Tone and Style | 장르 레이블 + 질감 형용사 2축 |
| Dialogue Weight | NPC 대사가 응답의 유의미한 비중 |

부수적으로, **CoT 안에서 초안을 미리 쓴다** — 대사 초안과 **문체 샘플 1줄**을
자기가 생성해 톤 앵커로 삼는다. 또 **UI 상태 변화에 감정 논리를 먼저 세우고**
그 결론으로 수치를 정한다.

## 5. graymar 과의 대조

### 5.1 겹치는 설계

| 그쪽 | graymar |
|---|---|
| PC 행동 예측 금지 | P0-H |
| 캐릭터 이미지 + 상태 태그 매칭 | arch/96 장면 컷 · arch/80 초상화 풀 |
| UI 블록 | `ServerResultV1.ui` |
| 대사 비중 규칙 | P2-A · P2-G |

### 5.2 아키텍처가 갈리는 지점

| 축 | 그쪽 | graymar |
|---|---|---|
| **상태 갱신 주체** | LLM이 호감도·상태를 판단해 출력 | **서버만** (불변식 1·2). 소프트 상태만 CAS 경유 |
| 판정 | 없음 (순수 서사형) | `1d6 + floor(stat/4)` · ResolveService |
| 이미지 선택 | LLM | nano confidence + 서버 게이트 |
| 규칙 검증 | 모델 자가점검 | 서버 후처리(R1~R7·마커 교정·IntroRollback) |
| CoT | 유저 노출 | 비노출 (`V7_no_leak`) |

상태 갱신을 LLM에 위임하면 서사와 수치가 자연히 붙지만 **일관성 보장이 없다**.
모델이 호감도를 임의로 되돌려도 막을 장치가 없다. 우리가 소프트 상태만 좁게
연 이유가 이것이다 — 이 축은 이식 대상이 아니라 **차별점으로 유지**한다.

### 5.3 정면 충돌 2건

**(A) 문체 샘플 앵커 ↔ 불변식 41·42**
우리는 `personality.signature` 노출 금지, speechStyle 어구 예시 금지다 — 정적
어구 풀은 positive/negative 무관하게 anchor가 된다(실측 근거 arch/56).
그쪽은 구체 문장을 앵커로 쓴다.

차이는 **"정적 풀 주입" vs "매 턴 새로 생성"** 이다. 우리가 금지한 것은 *고정
목록을 매 턴 같은 내용으로* 주입하는 것이고, 저쪽은 *그 턴 장면에 맞는 샘플을
매번 새로* 만든다. 후자는 앵커가 매턴 달라져 반복 위험이 구조적으로 낮다.
→ 불변식의 **취지는 지키면서 효과를 얻는 우회로**일 수 있다. 소유자 결정 필요.

**(B) 내적 독백 ↔ P1-D**
우리 P1-D는 내면 직접 서술 금지(외면 행동·표정·시선으로만)이고, 그쪽은 내적
독백이 중심 장치다. 이것은 우열이 아니라 **시점 구조의 귀결**이다.

- graymar: 2인칭("당신") — NPC 내면을 쓰면 시점이 깨진다
- 그쪽: NPC에 3인칭 제한 시점 — 그 인물의 내면을 합법적으로 쓴다

저 게임의 심리 묘사 깊이는 프롬프트 기교가 아니라 **시점 설계에서 나온다.**
같은 것을 원하면 프롬프트가 아니라 시점을 바꿔야 하고, 그것은 게임 정체성
변경이다. → **기각 권고.**
