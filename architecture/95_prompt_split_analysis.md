# 95. 프롬프트 이분할(서술계·대사계) 재검토 — 분석

> 상태: 📎 분석 (원형 재기각 권고 + 조건부 대안 1건)
> 작성: 2026-07-27. 소유자 제안("시스템·마커계 / NPC 대사계를 반씩 나눠 각각 표출 후 병합")에 대한 타당성 분석.
> 근거 데이터: 배포 후 24턴 프롬프트 실측(§2), arch/32·35·26·65·67 이력, llm-worker/dialogue-generator 현행 코드.

## 1. 제안 요약과 핵심 제약

제안: 현재 단일 메인 LLM 호출이 싣는 프롬프트(~13k자, 대화 연속 턴 ~16k자)를
**서술계(시스템 규칙+마커+장면·기억)** 와 **NPC 대사계(감정·말투·반응·직전 발언)** 로
이분할해 각각 호출하고 출력을 병합한다.

핵심 제약(소유자 확인): **이 트랙은 과거에 폐기됐다** — 병합이 마지막 토큰까지
기다려야 해서 스트리밍을 온전히 쓰지 못했기 때문. 본 분석은 "스트리밍 보존 여부"를
1급 기준으로 놓는다.

## 2. 현행 실태 (2026-07-27 실측)

- 일반 턴 = **메인 LLM 1회** (stream:true). 서술+대사를 한 출력으로 생성,
  StreamClassifier가 따옴표 기준으로 실시간 분리, NpcDialogueMarker가 사후 마커 보정.
- 예외적 분리 호출 2종만 존재: **자기소개 사전 생성**(arch/66, `firstMeetIntroId` 트리거)과
  **대사 누락 보강**(`appendMissingDialogue`). 즉 "좁은 태스크 분리"만 살아 있다.
- **제안과 동일한 구조가 이미 arch/32에 완제품으로 구현**되어 있다(Stage A segments JSON
  + dialogue_slot → Stage B nano 병렬 대사 생성 → 서버 병합·마커 직접 삽입).
  그러나 `llm-worker.service.ts:3401`의 `if (useJsonMode)` 게이트에 종속되어,
  현행 권장 설정(`LLM_JSON_MODE=false` + 스트리밍)에서는 **도달 불가능한 dead code**다.
- 프롬프트 총량(압축 후, 표본 24턴): avg 12,683자(≈7.7k tok), p50 13,784자,
  max 16,501자. 무거운 대화 연속 턴 구성비 ≈ 시스템 37% / NPC 컨텍스트·지시 27% /
  기억·연속성 15% / 턴 상태 10% / 서술 지시 5%.

## 3. 왜 폐기됐고, 왜 그 사유가 지금도 유효한가

### 3.1 구조적 상호 배타 (폐기 사유의 정체)
Stage B 병합은 Stage A의 **JSON 전체 응답을 파싱한 뒤에야** slot을 채울 수 있다.
스트리밍은 반대로 대사가 메인 출력에 **인라인으로 존재해야** 따옴표 감지·즉시 emit이
성립한다 (arch/35 §1.9: JSON 모드 = 스트리밍 표시 차단). 두 요구는 양립 불가 —
이분할을 켜는 순간 TTFB 2.2초(실측)가 "전체 생성+병합 완료 후"로 후퇴한다.

### 3.2 지금 조건에서는 더 나쁘다
- 메인 모델 처리시간 실측(저녁): Gemma 31B 17.9s/턴, DeepSeek 13.8s/턴.
  직렬 병합이면 사용자는 첫 글자까지 그만큼을 그대로 기다린다 (현행은 2.2초).
- 병합 정합성 비용은 실측 이력이 많다: Stage A speaker_id 오기(퍼지 매칭 3단 방어
  필요), Stage B 어체 위반 검증-재시도-템플릿 사다리, 이중 마커 잔해(버그 fc14ed2b),
  카드/서술 순서 역전(arch/67). 병합 지점이 늘수록 이 클래스 버그가 늘었다.
- 다단 호출 오류율 실측(arch/67): NpcReaction JSON 파싱 실패 10.4%, 워커 이중 처리
  1.1%. 대사계 호출을 매 턴 추가하면 이 실패 클래스가 매 턴 노출된다.

### 3.3 토큰 수지 — 이득이 기대보다 작다
분할 시 각 호출은 절벽(11k tok)에서 멀어지지만(호출당 ≈8k자 ≈ 4.9~5.2k tok),
공유 컨텍스트(행동·판정·장면·직전 발언·시스템 코어)가 **양쪽에 중복**되어 총 입력은
+4% 안팎. 비용은 입력 기준 +70~90%/턴(현 ₩1.57 → ₩2.7~3.0). 반면 압축(arch/79 2차,
2026-07-27)만으로 이미 avg 7.7k tok·상한 도달 1/24턴을 달성해, "절벽 회피"라는
분할의 최대 명분이 상당 부분 소멸했다.

## 4. 스트리밍을 보존하는 변형 2종 검토

### 4.1 병렬 A∥B + 슬롯 지연 충전 — ❌ 기각
Stage A를 즉시 스트리밍하고 슬롯 지점에서 B 결과를 끼우는 안. 슬롯이 산문에
존재하려면 A가 슬롯 토큰(`@@SLOT@@` 류)을 생성해야 하는데, 이는 (a) 새 마커의
미생성·변형 실패 모드를 추가하고 (b) 대사가 서술 초반에 몰리는 실제 출력 패턴상
첫 슬롯에서 스톨 확률이 높으며 (c) StreamClassifier·후처리 전 파이프라인이 슬롯
인지형으로 재작성돼야 한다. 정합성 비용이 원형보다 크다.

### 4.2 대사 선행 생성 → 메인 주입 (역전 설계) — ⚠️ 조건부 검토 가치
분할하되 병합 방향을 뒤집는다: 대사계를 **선행 경량 호출**(DialogueGenerator,
입력 = 행동·판정·감정·직전 발언 — 모두 턴 커밋 시점에 확보됨)로 1~2문장 확정하고,
메인 프롬프트에 positive 주입한다. 병합이 LLM 내부에서 일어나므로 **스트리밍이
완전 보존**된다. 이미 검증된 패턴의 확장이다:
- 자기소개(arch/66): nano 사전 생성 → positive 주입 → 미반영 시 서버 삽입 —
  성사 0% → 보장으로 만든 유일한 "분리가 실측으로 이긴" 사례.
- NpcReactionDirector(arch/56): 반응·즉시목표·톤 3축을 이미 선행 확정 중.
  같은 nano 왕복에 대사 초안을 얹으면 추가 레이턴시 ≈ 0.

기대 이득: 메인 프롬프트에서 NPC 대사 규칙·컨텍스트 일부(감정 행동힌트 상세,
말투 가이드, 어체 지시 등 ~1.5~2k자)를 덜어낼 수 있고, 어체·호칭은 좁은 태스크
(검증 가능)에서 생성되므로 준수율이 오른다 (자기소개 어체 검증 사다리 재사용).

리스크: ① 선행 대사가 메인 서술 전개와 어긋날 가능성(완화: nano가 이미 반응·톤을
선결정하므로 같은 컨텍스트면 정합) ② 메인 LLM의 주입 대사 변형(완화: 자기소개식
검증+서버 삽입 사다리) ③ nano 파싱 실패 10.4% 클래스가 매 턴 대사에 노출(완화:
실패 시 현행 단일 호출로 자연 격하 — 주입만 생략하면 됨, 킬스위치 무비용).

## 6. 결론

1. **이분할 원형(각각 호출 후 병합)은 재기각을 권고한다.** 폐기 당시 사유(스트리밍
   상실)가 구조적 상호 배타로 확인되고, 지금은 모델이 더 느려져(17.9s/턴) 그 대가가
   커졌으며, 압축(arch/79 2차)으로 분할의 최대 명분(절벽 회피)이 이미 상당 부분
   달성됐다. 총 토큰도 중복 때문에 오히려 +4% 안팎이다.
2. 분할의 이점(호출당 규칙 밀도 완화, 어체 준수)을 원하면 **§4.2 역전 설계**가
   유일하게 스트리밍을 보존하는 경로다. 단, 착수 트리거는 "어미 일치율이 한산
   시간대 재측정에서도 저조할 때"로 둔다 — 현재의 68~75%가 프로바이더 혼잡
   교란인지 미확정이므로.
3. 어느 쪽이든 선행 조건은 재비대 가드(플레이테스트 센서에 프롬프트 총량·백스톱
   발동률 지표)다. 크기 문제를 구조 변경으로 풀기 전에, 크기가 다시 자라는 것을
   막는 계측이 먼저다.

## 7. 역전 설계 파일럿 실측 (2026-07-28, spike/dialogue-precommit a7d5a2a)

§4.2를 최소 구현해 실측했다. 구현: 대화 계열 LOCATION 턴에서 NpcReactionDirector
결과를 입력으로 `LLM_DIALOGUE_MODEL`이 핵심 대사 1~2문장을 사전 생성(어체 기계
검증, 실패 시 무주입 격하), `[P0 — NPC 확정 대사]`로 positive 주입. 스트리밍 무변경.
측정: chat-edric·chat-ronen 감사, 동일 아침 시간대 비파일럿 런과 대조.

| 지표 | 비파일럿 (동일 시간대) | 파일럿 | 판정 |
|---|---|---|---|

| 어미 일치 (로넨·합쇼체) | 80% | 80% | ― 정체 (원인 아래) |

**판정.**
1. **핵심 메커니즘은 실증됐다** — 사전 확정 대사는 94%가 축자 채택되고, 그 대사의
   어체·호칭은 기계 검증으로 보장된다. 에드릭 어미 94%는 7/08 기준선(89%) 이상.
2. **커버리지 한계** — 로넨 어미가 정체한 이유는 주입이 1~2문장만 커버하고, 부속
   발화(문장 수 기준 절반+)는 여전히 메인 LLM(DeepSeek 68%) 몫이기 때문. 완전
   해결은 부속 발화 억제 강화 또는 어미 후처리 확장과의 병행이 필요하다.
3. **부작용 1건 — 응답률 급락 (채택 전 보완 필수)**: 확정 대사가 플레이어 발화의
   구체 단어를 되받지 않아(생성 프롬프트의 "복창 금지" + 협소한 입력 컨텍스트)
   NPC가 자기 대본으로 답하는 인상 — 에드릭 응답률 70→30%. "대화가 이어지는
   NPC"라는 원목표와 상충. 보완안: 생성기에 "상대 발화의 핵심 명사 1개를
   자연스럽게 되받을 것" positive 지시 추가 후 재측정.

**결론**: 도입 가치 있음(어미·호칭 보장 경로 실증, 스트리밍·레이턴시 무손실).
단 응답률 회귀 보완 → 재측정 관문 통과 전에는 main 병합 금지. 브랜치는
spike/dialogue-precommit 유지 (관문 통과 시 feat/* 이관 — 브랜치 정책).
