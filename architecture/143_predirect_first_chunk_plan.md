## 0. 지금 어디에 시간이 드는가 (실측)

최근 3일 운영 로그(`[TurnTiming:WORKER]` 40턴)와 `llm_call_logs` 기준이다.

| 구간 | 전형 | 꼬리 | 비고 |

**사전 결정 꼬리 6턴의 원인은 두 가지다.**

1. **NPC 반응 JSON 파싱 재시도** — 같은 턴에 `npc-reaction` 호출이 2번 찍힌 턴 3개(c91a2d64 T8·T10, 7fe920e6 T9). 1.6초 + 1.6초가 직렬로 붙는다. 과거 실측 파싱 실패율은 10.4%다(nano 감사 3번).
2. **지목 NPC 없는 턴의 직렬 실행** — 장소 첫 턴(T4)처럼 `actionContext.primaryNpcId` 가 비면, 연출 nano 가 NPC 를 고른 **뒤에야** 반응 nano 가 시작된다(2.85~2.97초). 14일 장소 턴 81개 중 10개(12%)가 이 경로였다.

나머지 하나(bab64df8 T12, 3.9초)는 반응 nano 단발 지연이다.

**두 nano 의 바닥값.** 연출 nano p50 1.42초, 반응 nano p50 1.62초 / p90 2.17초다. 출력은 각각 120~150토큰, 170~190토큰이다. 아주 짧은 프롬프트로 gpt-4.1-nano 를 직접 찔렀을 때 첫 토큰이 0.7~0.9초였다. 따라서 반응 nano 1.6초는 대략 첫 토큰 0.8초 + 생성 0.8초다.

**서술 첫 토큰의 바닥값.** 아주 짧은 프롬프트(“안녕이라고만 답해”)로 GPT-6 Luna 를 4회 찔렀더니 첫 토큰이 **1.3~1.6초(1회 2.5초)** 였다. 실제 서술 프롬프트(약 8천 토큰)의 첫 토큰 1.0~1.8초와 같다. 64턴을 캐시 안 된 토큰 수로 나눠 봐도 첫 토큰 중앙값이 1.34 / 1.33 / 1.28초로 차이가 없었다. **첫 토큰은 프롬프트 길이나 캐시가 아니라 모델·경로의 고정 지연이다.** 이 결과가 작업 5 의 방향을 바꾼다(§3).

## 1. 작업 3 — 사전 결정 단축

### 3-1. 꼬리 상한 (낮은 위험, 바로 진행 가능)

- **두 nano 를 JSON 모드(`response_format: json_object`)로 부르고 파싱 재시도 루프를 없앤다.** 형식 오류는 사라지고, 값이 틀리면 기존 `buildFallback` 으로 간다. (계획 초안은 strict JSON 스키마였으나 실측에서 기각 — §4)
- **요청 단위 상한은 arch/142 R2 옵션을 쓴다** — `{ maxRetries: 0, fallback: false }`, `timeoutMs` 3000. **요청 타임아웃만으로는 상한이 지켜지지 않아**(§4) 호출 쪽에 3초 마감(`raceNanoDeadline`)을 따로 건다.
  - 지금은 기본 재시도 2회 + fallback 모델(gpt-4.1-mini) + 파싱 재시도 루프라서, 최악이 5초 × 4회까지 갈 수 있다.
  - 3초를 고른 이유: 반응 nano p90 이 2.17초다. arch/142 처럼 2.5초로 자르면 약 8% 가 기본값으로 떨어진다.
- **연출 nano 가 실패하면 NanoDirector 를 다시 부르지 않는다.** 지금은 `nanoEventCtx` 가 있는데 연출 nano 가 실패하면 `nanoDirector.generate` 를 **직렬로** 한 번 더 부른다(+1.2초). NanoDirector 폴백은 `nanoEventCtx` 자체가 없는 턴에만 남긴다. 실패 턴은 연출 힌트 없이 서술한다.
- 기대: 꼬리 2.9~3.9초 → 약 1.9초, 최악 3초. 평균 −0.3초 안팎, p90 −1.5초.
- 감시: 기본값 폴백 비율(`[NpcReaction] ... source=fallback`)과 연출 nano 실패 로그를 첫 주 집계한다.

### 3-2. 지목 NPC 없는 턴 — 후보 동시 실행 (낮은 위험)

- `primaryNpcId` 가 없으면, `nanoEventCtx.presentNpcs` 앞쪽 최대 3명의 반응 nano 를 **연출 nano 와 동시에** 시작한다. 연출 nano 가 고른 `npcId` 의 결과만 쓰고 나머지는 버린다. 고른 NPC 가 후보 밖이면 지금처럼 직렬로 실행한다.
- `applyEmotionalShiftHint`·관계 신호·계측은 채택된 NPC 하나에만 적용한다. 버린 결과는 어디에도 쓰지 않는다.
- 0단계 확인: 30일 이 경로 턴에서 nano 가 고른 NPC 가 `presentNpcs` 앞 3명 안에 있었는지 재집계한다. 위 표본 25턴은 전부 안에 있었다.
- 기대: 해당 턴(약 12%) −1.5초. 비용은 그 턴에만 nano 1~2회가 늘어난다(턴 평균 1% 미만).

### 3-3. 사전 결정 nano 를 더 빠른 모델로 — 벤치 후 소유자 결정 (중간)

3-1·3-2 를 해도 전형값 1.5~1.9초는 그대로다. 그 바닥은 gpt-4.1-nano 의 첫 토큰(0.8초)과 생성 속도다. 전형값을 줄이는 가장 큰 손잡이다(장소 턴 전부 해당).

1. **실제 요청 수집.** 기존 `PROMPT_FIXTURE_CAPTURE` 경로를 넓혀 두 nano 의 요청 메시지를 스크래치에 덤프한다. 운영에서는 켜지 않고, 형식 테스트(5~10턴)를 몇 판 돌려 60건 이상 모은다.
2. **재생 벤치.** OpenRouter 에서 고처리량 + `json_schema` 지원 후보 2~3개와 현행 gpt-4.1-nano 를 같은 스키마로 돌린다(기존 `llm-config-ab.py` 확장).
   - 일치도 비교의 잡음 기준선은 현행 모델을 두 번 돌려 잡는다(arch/142 A/B 방식).
3. **관문 (전부 충족해야 채택):**
   - 스키마 유효 100%.
   - p50 0.9초 이하.
   - 반응 유형·거절 수준 일치율이 잡음 기준선 −5%p 이내.
   - 추상 톤 3축에 따옴표 인용·구체 동작이 섞이지 않는다(불변식 39·42 — 정규식 + 표본 정독).
   - 턴당 비용이 현행 이하.
4. **채택 방식.** 단계 전용 env `LLM_PREDIRECT_MODEL` 을 신설한다(기본값 = 경량 모델 → 미설정 시 동작 불변). 롤백은 .env 한 줄이다.
   - 모델 교체라서 결과를 보고 소유자가 정한다.
   - **업스트림 프로바이더가 바뀌면 개인정보처리방침의 국외 이전 목록(arch/107)도 함께 고쳐야 한다.**
- 기대: 관문을 통과하면 사전 결정 1.6초 → 0.6~0.9초(장소 턴 전부 −0.7~1.0초).

### 3-4. R2 선택지 사전 계산 — 보류 권장 (조건부 재개)

선택지 턴(65%)에서 클릭 전에 사전 결정을 끝내 두는 안이다. 지금 구조에서는 효과가 작고 비용과 정합 위험이 크다.

- **연출 nano 는 미리 못 돈다.** 입력인 `nanoEventCtx` 는 POST 의 이벤트 매칭 결과다. 이벤트 매칭은 RNG 커서를 소비한다(불변식 4). 선택지마다 POST 를 투기 실행하는 것은 부작용 때문에 안전하지 않다.
- **반응 nano 만 미리 돌려도 이득이 ≤0.3초다.** 두 nano 가 병렬이고 길이가 비슷해서, 반응 쪽만 빼도 연출 nano 1.4초가 그대로 남는다.
- **입력이 낡는다.** 반응 nano 는 POST 가 갱신한 NPC 감정 상태(`llmContext.npcStates`)와 판정 결과를 본다. 클릭 전에는 둘 다 없다. CHECK 선택지는 결과 3종을 각각 계산해야 한다.
- **비용.** 선택지 3~4개 × (CHECK 면 ×3)로 nano 호출이 턴당 3~10회 는다. 지금 턴당 약 1.7원인데 1.4~3.5원이 더 붙는다.

**재개 조건:** 연출 nano 를 서술 호출로 흡수하는 A/B(arch/141 개선안 4)가 통과하고, 3-3 이 실패해서 반응 nano 가 유일한 사전 결정으로 남을 때. 그때는 반응 nano 하나만 선택지별로 미리 돌리면 선택지 턴의 사전 결정이 0에 가까워진다.

## 2. 작업 5 — 첫 조각 앞당기기

### 5-1. 첫 서술 조각을 절 경계에서 내보내기 (낮은 위험)

- `StructuredNarrativeStream` 의 서술 분기는 지금 문장 끝(`[.!?…。]` + 공백·줄바꿈)에서만 자른다. **턴의 첫 송출에 한해**, 문장 끝이 아직 없고 12자 이상 쌓였으면 마지막 절 경계(`,` `;` `:` `—` + 공백)에서도 자르게 한다. 둘째 조각부터는 지금처럼 문장 단위다(타이핑 리듬 유지).
- **안전성:**
  - 절 경계는 어절을 쪼개지 않는다. 그래서 조각별 실명 가리기(`sanitizeStreamSegment` → `maskHiddenNpcNames`, 불변식 51)가 그대로 성립한다. 공백에서 자르면 `토브렌 하위크` 같은 다어절 이름이 두 조각으로 갈라져 Phase A 보호가 깨지므로, 공백 경계는 쓰지 않는다.
  - 클라이언트는 같은 문단의 조각을 공백으로 이어 붙인다(`StreamingBlock` `join(' ')`). 쉼표 뒤 타이핑 정지(`charSpeed × 2`)도 이미 있다.
  - 저장본은 스트림 완료(`finish`) 결과라 영향이 없다.
- 스펙: 첫 조각 절 경계 분할 · 12자 미만 미분할 · 둘째 조각부터 문장 단위 · 쉼표 직전 미소개 실명 가리기 · `paragraphStart` 가 첫 조각에만 붙는지.
- 기대: 첫 조각 −0.2~0.3초(현재 첫 토큰 → 첫 조각 0.3~0.7초).

### 5-2. 프롬프트 캐시 — 지연 목적으로는 하지 않는다

- 실측상 캐시는 이미 동작한다. 서술 프롬프트 평균 7,924토큰 중 3,660토큰(46%)이 캐시되고, 시스템 메시지 전체가 매 턴 같다.
- 캐시 접두는 기억 블록 첫 80자 근처에서 끊긴다. 첫 블록 `[세계 상태]` 가 매 턴 바뀌기 때문이다. 런·장소 단위로 고정인 블록(`[주인공 배경]`·`[등장 가능 NPC 목록]`·`[장소 기억]` 등)을 앞으로 옮기면 약 800토큰(+10%p)을 더 캐시할 수 있다.
- 그러나 §0 실측대로 **첫 토큰은 캐시 안 된 토큰 수와 무관하다.** 블록 순서 변경은 서술 품질 위험(arch/79 순서 튜닝)이 있는데 지연 이득이 없다.
- **판단:** 지연 계획에서 빼고, 필요하면 비용 항목으로 따로 다룬다.
  - 순서 변경 없이 `prompt_cache_key`(런 단위)를 OpenRouter 가 전달하는지만 확인한다.
  - 캐시가 통째로 빗나간 턴(6%, 캐시 25% 미만)이 줄어드는지 본다.

### 5-3. 서술 첫 토큰 바닥 1.3초 — 이 계획 밖

이 바닥은 모델·경로에서 온다. 줄이려면 서술 모델·프로바이더를 바꾸거나 구조를 바꿔야 한다(arch/141 R4 2막 서술: 짧은 첫 막을 먼저 스트리밍). 둘 다 소유자 결정 사항이라 여기서는 기록만 한다.

## 4. 구현 결과 — A (2026-10-12)

**계획에서 바뀐 두 가지 (실측 근거)**

- **strict JSON 스키마 → `json_object`.** 같은 반응·연출 요청 40건을 세 방식으로 교대 재생했다.

  | 방식 | p50 | p90 | JSON 유효 |
  |---|---|---|---|
  | strict `json_schema` | 2.13초 | **3.17초** | 40/40 |
  | `json_object` | 1.81초 | 2.23초 | 40/40 |
  | 지정 없음 | 1.76초 | 2.19초 | 39/40 |

  strict 스키마는 제약 디코딩으로 느려지고, p90 이 3초 상한에 걸려 오히려 기본값 폴백을 늘린다. 운영 1차 배포(스키마)에서도 사전 결정 중앙값이 1.92 → 1.99초로 올랐다.
- **호출 쪽 3초 마감.** `timeoutMs` 3000 인데 반응 nano 가 3.47초에 성공한 기록이 나왔다. OpenRouter 가 non-stream 요청에도 헤더를 먼저 보내 SDK 타임아웃이 본문 대기를 끊지 못하는 것으로 본다. `raceNanoDeadline` 으로 마감 뒤에는 기다리지 않고 기본값으로 간다(늦은 원 요청은 버리되 비용 계측은 남는다).

## 6. 커밋 전 `/review` 후속 (2026-10-12)

전문 리뷰어 5명 + Red Team + adversarial 3패스(2회 수정 후 수렴). 반영:

- **처리되지 않은 거부:** 채택되지 않은 후보 반응 promise 에 `.catch`. Node 22 + 핸들러 부재라 거부 하나가 서버 프로세스를 내릴 수 있었다.
- **레이트 리미터 우선순위:** 연출 nano 를 후보 반응보다 먼저 시작하고, 후보 수를 `LlmCallerService.rateHeadroom()` 여유 안으로 제한한다. 전역 버킷(버스트 10·초당 3)을 투기 호출이 마이너스로 끌어내리면 연출 nano 가 3초 마감을 넘기고 다른 플레이어의 서술 스트림도 늦어진다.
