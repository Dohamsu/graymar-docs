# 89. 사례금 귀속 재설계 — 지급 주체 명시 + 정산 시점 분리 (2026-07-25)

## 배경 (실측)

arch/65 경제 루프 v1은 "단서를 캐서 받은 사례금으로 입을 닫은 자의 입을 연다"는
루프를 세웠고, 소스로 `quest.json rewards`(factGold 5 / transitionGold 10~25)를
fact 발견·questState 전환 시점에 **즉시 지급**했다. 수치 밸런스는 의도대로
작동했으나, **"누가 준 돈인가"가 게임 안에 존재하지 않는** 결함이 남아 있었다.

### 결함 1 — 지급 주체 없음

지급 조건에 NPC·의뢰인 접촉·보고 행위가 일절 없다. `addFact()` 호출마다 무조건
factGold가 붙는다(turns.service `applyQuestProgression`). 그래서 혼자 물건을 들여다본
INVESTIGATE, 그림자에 숨어서 지켜본 OBSERVE 턴에도 골드가 솟았다.

코드 주석에는 "서사 명분: 의뢰 경비 지원(프롤로그의 의뢰인 구조)"이라 적혀 있었으나
그 명분은 **주석에만 존재**했고 게임 내 전달 경로가 없었다.

### 결함 2 — LLM이 현장 NPC에게 임의 귀속 (더 큰 문제)

`prompt-builder`의 `[이번 턴 사건]` 블록은 서버 이벤트를 그대로 주입한다:

```
[이번 턴 사건]
- [GOLD] [사례금] 조사 진전의 대가 10골드
```

LLM은 이를 "이번 턴에 일어난 일"로 받아 서사화하는데, 장면에 등장하는 인물이 그 턴의
primary NPC뿐이니 **그 NPC가 돈을 건네는 장면을 지어냈다.**

전체 DB 실측 (사례금 이벤트 발생 72턴):

| 지표 | 건수 | 비율 |
|---|---|---|
| 서술에 돈/은화/주머니 언급 | 42 | 58% |
| 명시적 "NPC가 건네는" 서술 | 25 | 35% |

행동별 오귀속 (사례금턴 / NPC가건넴): INVESTIGATE 23/11 · TALK 18/8 ·
PERSUADE 14/3 · OBSERVE 11/1 · BRIBE 3/1 · THREATEN 1/1.

실제 파탄 사례:

- **THREATEN** "이렌을 추궁해봐" → 추궁당한 상대가 *"품속에서 돈 주머니를 꺼내 조용히
  건네고, 별기름 램프 하나를 함께 내민다"*
- **OBSERVE** "그림자에 숨어서 상황을 지켜본다" → 숨어 있는데 루오르가 *"품 안에서 작은
  돈 주머니를 꺼내 탁자 위에 내려놓는다. 20골드가 당신의 몫으로 남겨진다"*
- **INVESTIGATE** "불꽃이 눕는 방향을 살핀다" → NPC 무관 물리 관찰인데 누군가 돈+램프를 건넴

`transitionEquipment`(순찰대 경갑·별기름 램프·꿈 나침반)도 같은 경로라 약초 파는
노부인이 순찰대 경갑을 대주는 식의 장면이 생겼다.

### 결함 3 — BRIBE 순이익 역전

뇌물 6G를 쓴 턴에 전환 사례금 15G가 겹치면 순 +9G. arch/65가 설계한 "정보 구매는
소폭 적자(-1G)" 균형이 전환 턴마다 뒤집혔다.

### 불변식 2의 사각지대

LLM은 하드 상태를 *변경*할 수 없지만(불변식 2), 하드 상태 변화를 **틀린 인과로
설명**하는 것은 어떤 게이트로도 막히지 않는다. 이 건이 정확히 그 사각지대다.

## 설계 — C(주체 명시) + B′(정산 시점 분리)

검토 시 두 방향이 후보였다.

- **B(보고 시 정산)** — 의뢰인에게 보고할 때 정산
- **C(귀속 명시)** — 이벤트 텍스트에 지급 주체를 박아 LLM 임의 귀속 차단

둘은 배타가 아니라 **C가 B의 전제**다. B의 "보고 대상"을 정의하려면 지급 주체
npcId를 콘텐츠 계약으로 먼저 세워야 하기 때문이다. 다만 B를 원안대로(의뢰인 대면
단독 트리거) 가면 세 가지 위험이 있어 **완화형 B′**로 조정했다.

| B 원안의 위험 | B′의 대응 |
|---|---|
| 왕복 강요 — 의뢰인은 NpcSchedule로 이동, 찾아가는 데 2tick. "돈 받으러 가라"가 불변식 47(의도 존중)·arch/76 D1(강제 진행 = 최다 이탈 요인)과 충돌 | 거점 복귀 자동 정산을 안전판으로 병설 |
| 미보고 시 소스 사장 — 안 찾아가면 골드가 영영 미지급, arch/65 이전 상태로 회귀 | 거점 복귀 + 런 종료 정산으로 사장 방지 |
| star_sand 후반 접근 불가 — 의뢰인 이렌은 S3_INSIDE 이후 꿈 속 동선. 사례금 최대 구간(20/25G)이 여기 | 거점 정산이 커버 |

### 한 문장 규칙

> **단서를 캐면 장부에 쌓이고, 의뢰인을 만나거나 거점으로 돌아오면 정산된다.**

## 구현

### C — 지급 주체 콘텐츠 계약

```jsonc
// content/<pack>/quest.json (최상위)
"clientNpcId": "NPC_RONEN",
```

| 팩 | 의뢰인 | npcId | tier |
|---|---|---|---|
| graymar_v1 | 로넨 | `NPC_RONEN` | CORE |
| silverdeen_v1 | 도른 (여관 주인) | `NPC_SD_INNKEEP` | SUB |
| star_sand_v1 | 이렌 (꿈잠 여관 주인) | `NPC_SS_IREN` | CORE |
| karnholt_v1 (AUTONOMOUS) | — | quest.json 자체가 없어 사례금 0 — 무영향 |

조회 API (`QuestProgressionService`):

- `getQuestClientNpcId()` — quest.json `clientNpcId`가 정본, 미정의 팩은
  `prologue.npcId`(의뢰를 준 인물) fallback, 둘 다 없으면 null
- `getQuestClientDisplayName()` — npcs.json에서 표시명 파생 (불변식 45: 엔진에
  콘텐츠 리터럴 금지, 로더 파생 API로만 접근)

세 팩 모두 `prologue.npcId`가 의뢰인과 일치해 fallback만으로도 동작하지만, 두
개념(프롤로그 화자 ≠ 의뢰인)이 갈리는 팩이 나올 수 있어 명시 필드를 정본으로 둔다.

### B′ — 적립 → 정산

`RunState.pendingQuestReward: { gold, equipment[], sinceTurn } | null`

fact 발견·단계 전환 시 **즉시 지급하지 않고 적립**한다. 정산은 지급 주체가 납득되는
세 시점에만 (`settlePendingQuestReward`, source 인자로 구분):

| 트리거 | 시점 | 서사 명분 |
|---|---|---|
| `CLIENT_MEETING` | LOCATION 턴에서 `event.payload.primaryNpcId === clientNpcId` | 의뢰인이 직접 건넨다 |
| `HUB_RETURN` | `returnToHubFlow` (거점 복귀) | 연락책 경유 정산 — 왕복 강요 회피 안전판 |
| `RUN_END` | 엔딩 확정 턴 | 미수령분 사장 방지 (아카이브 최종 골드 정합) |

정산 시 골드 가산 + 적립된 `transitionEquipment` 인스턴스 생성 + ItemMemory 기록을
한 번에 처리하고 `pendingQuestReward`를 비운다.

### 이벤트 분리

| 상황 | kind | tags | 텍스트 |
|---|---|---|---|
| 적립 | `QUEST` | `QUEST_REWARD_ACCRUE` | `[사례금 적립] 조사 진전 5골드 — 로넨에게 받을 몫 (누계 15골드)` |
| 정산(대면) | `GOLD` | `QUEST_REWARD_SETTLE` | `[사례금] 로넨의 경비 지원 15골드` |
| 정산(거점) | `GOLD` | `QUEST_REWARD_SETTLE` | `[사례금] 로넨이 보낸 경비 15골드` |
| 정산(종료) | `GOLD` | `QUEST_REWARD_SETTLE` | `[사례금] 로넨와의 셈을 마쳤다 — 15골드` |
| 장비 정산 | `LOOT` | `QUEST_REWARD_SETTLE` | `[사례금] 로넨가 대준 의뢰 장비 — 순찰대 경갑` |

적립 이벤트는 `kind: 'QUEST'`다 — 골드가 아직 늘지 않았으므로 GOLD로 두면 HUD와
어긋난다. `diff.inventory.goldDelta`에는 **정산액만** 반영된다(적립액 아님).
`memoryCollector`에 넘기는 goldDelta도 동일 기준(`questSettledGold`).

### A — 프롬프트 게이트

`prompt-builder`의 `[이번 턴 사건]` 필터에 `QUEST_REWARD_ACCRUE` 제외를 추가.
지급 주체가 장면에 없는데 금액을 프롬프트에 넣으면 LLM이 임의 귀속시키므로,
**적립은 LLM에게 보이지 않는다.** 반대로 `QUEST_REWARD_SETTLE`은 주체가 텍스트에
명시돼 있고 대면 정산 턴은 의뢰인이 화자이므로 그대로 전달한다.

fact 공개 자체는 `ui.questReveal` 별도 경로(arch/58)라 이 필터의 영향을 받지 않는다.

### HUD

`UIBundle.pendingQuestReward { gold, equipmentCount, clientName }` 신설 →
클라 `PlayerHud.pendingQuestGold` → Header 골드 옆 `(+15)` 회색 표기 + 툴팁
("의뢰인을 만나거나 거점으로 돌아가면 정산됩니다"). 데스크톱·모바일 상태줄 양쪽.

미정산 잔액이 항상 보여야 정산 지연이 버그가 아니라 규칙으로 읽힌다. 이어하기는
`getRun` 응답의 `runState` 통짜 전달로 자동 복원된다(별도 배선 없음).

클라 갱신 규칙: 서버가 `ui.pendingQuestReward`를 보내면 그 값, 없고
`QUEST_REWARD_SETTLE` 이벤트가 있으면 0, 둘 다 없으면(전투 등 무관 턴) 기존 잔액 유지.

### 실런 2 — 강압 페르소나 (coercer 15턴, 원래 파탄이 가장 심하던 조건)

즉 **사례금이 NPC에게 귀속된 서술은 0건**. T8 거점 정산도 `로넨이 보낸 경비 40골드`로
조사 처리(`korParticle`)까지 정상.

### 게이트 실패 3건 — 전부 인과 배제

같은 날 5런(변경 전 2 + 변경 후 3)을 대조해 실패의 인과를 확인했다.

| 게이트 | 발생 | 판정 기준 | 인과 배제 근거 |
|---|---|---|---|
| `V9_quality` | 2차만 | `haoSoRatio` 0.545 (임계 0.6) | **3차 동일 페르소나에서 0.6 PASS → flaky.** 변경 전 런 0.61·0.73, 변경 후 chatty 0.65. NPC 어체 준수율은 본 변경 3경로(이벤트 텍스트 / 프롬프트 1줄 제외 / 지급 타이밍) 어디와도 무관 |
| `V2_encounter` | 3차 | 조우 NPC ≥ 2 | **변경 전 런(13:30)에서도 동일 실패.** 짧은 런에서 한 NPC에 집중하면 발생하는 표본 문제 |
| `V5_memory` | 3차 | `structuredMemory.visitLog` 비어 있지 않음 | 3차는 HUB 턴이 프롤로그 2개뿐 — **장소 방문 종료(HUB 복귀)가 0회**라 visitLog가 빌 수밖에 없다. `returnToHubFlow`에서 정산은 `finalizeVisit` **이후**에 붙였으므로 순서 영향도 없음 |

즉 3런 모두에서 사례금 관련 회귀는 0이며, 실패한 게이트는 페르소나·런 길이에
따른 기존 변동이다.

## 팩 계약 (신설)

`quest.json`에 `rewards`(사례금)를 정의하는 팩은 `clientNpcId`를 함께 정의한다.
미정의 시 `prologue.npcId`로 fallback되지만, 프롤로그 화자와 의뢰인이 다른 팩은
반드시 명시해야 한다. 주체가 끝내 없으면 적립·거점 정산은 동작하되 이벤트 텍스트에
주체가 빠진다(`[사례금] 밀린 조사 사례금 N골드`).

## 후속 (미착수)

- 의뢰인 대면 정산 턴의 LLM 서술 품질 — 정산 이벤트를 받은 턴에 의뢰인이 자연스럽게
  셈을 치르는 장면이 나오는지 표본 축적 후 판단. 필요하면 디렉티브 1줄 추가.
- 적립 누계가 커졌을 때 의뢰인을 찾아갈 유인(이자·보너스) — 밸런스 데이터 축적 후.
- BRIBE 순이익 역전은 정산 분리로 같은 턴 상계가 사라져 완화되나, 전환 사례금 자체의
  곡선 튜닝은 별건으로 남는다.
