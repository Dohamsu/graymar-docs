# 101. 자기개선 하네스 루프 설계 — 코드·문서·DB 3소스 정합 감사 (2026-08-12)

> **상태**: 📎 설계 (미구현) · 결정 대기 3건 (§11)
> **성격**: 정적·데이터 감사가 본체이고, **회차당 단기 런 5회**를 유한 예산으로
>   붙인 하네스 루프. 플레이테스트(arch/79·98 게이트)가 "런이 잘 도는가"를 보는
>   반면, 이 루프는 **"코드·문서·DB가 서로 같은 말을 하는가"** 를 본다.
> **개정**: 2026-08-12 — 단기 런 5회 예산 허용(소유자). §7 검증 사다리 신설.

## 1. 왜 필요한가 — 이번 세션의 증거

2026-08-12 세션에서 나온 결함 7건은 전부 **플레이테스트·단위 테스트·게이트를
통과한 상태**로 존재했다. 실행은 정상이고 결과도 그럴듯했기 때문이다.

| # | 결함 | 어떻게 발견됐나 |
|---|---|---|
| 1 | `actionType`/`parsedType` 키 불일치 → nano 가 행동을 100% 오인 | 원값 로그 |
| 2 | `ui.equipmentTags`·`activeSetNames` 쓰기 지점 0 — 프롬프트 블록 영구 미출력 | 코드↔DB 대조 |
| 3 | `runState.lorebook` 쓰기 0 — 로어북 중복 필터 무효 | 코드↔DB 대조 |
| 4 | `actionContext.relatedIncidentId` 오위치 참조 | 코드↔DB 대조 |
| 5 | 감정 임계 60 vs fear p99 **0.0** — 행동화 4종 중 1종만 가동 | DB 분포↔코드 상수 |
| 6 | Stage B(arch/32) 광역 경로 사문화 — `LLM_JSON_MODE=false` | env↔코드 경로↔DB |
| 7 | 대사 소실 33.4% — 화자 오귀속 → F-aux 삭제 | DB 원문↔저장본 |

그리고 **문서도 틀려 있었다** — CLAUDE.md 는 "agitation 4종 전부 실발동 실증"
이라고 적고 있었으나 실측은 실질 1종(APPROACH)이었다.

공통점: **어느 하나도 "터지지" 않는다.** 폴백이 정상 동작하고, 조용히 기능만
꺼진다. 실행 기반 검증(플레이테스트)으로는 원리적으로 못 잡는 부류다.

## 2. 설계 원리 — 3소스 드리프트

이 레포에는 같은 사실을 주장하는 소스가 셋이고, 각자 따로 변한다.

```
   코드 (실제로 실행되는 것)
      ↕                  ↖
   DB (실제로 일어난 것) ↔ 문서 (일어난다고 믿는 것)
```

- **코드**: 121개 md 가 기술하는 대상. 매 커밋 변함.
- **DB**: 실유저 런의 실측. 코드보다 늦게 반영되고, 옛 코드 흔적이 남음.
- **문서**: 불변식 50개 + arch 90 + specs·guides 31. **가장 빨리 낡는다.**

결함은 항상 **두 소스의 불일치**로 나타난다. 루프의 정체는
"세 소스를 기계적으로 교차 대조하는 것" 이며, 그 이상도 이하도 아니다.

## 3. 디텍터 5족

각 족은 §1 의 실제 발견에서 역설계했다 — 가상의 위험이 아니라 **이미 한 번씩
터진 자리**다.

### A. 불변식 감시 (문서 → 코드·DB)

CLAUDE.md `Critical Design Invariants` 50개 중 **기계 검증 가능한 것**을
질의로 등록하고 매 회 재검한다. 이 루프의 최고 가치 항목 — 불변식은 이 레포의
설계 계약인데 지금은 **아무도 검증하지 않는다**.

초벌 분류(§11-②에서 확정): 완전 검증 가능 ~25 · 부분 ~15 · 불가 ~10.

바로 등록 가능한 고가치 예:

| 불변식 | 검증 |
|---|---|
| #3 Idempotency | 유니크 제약 2종 존재 여부 (DDL) |
| #6 Action slot cap = 3 | `actionSlots > 3` 인 턴 수 = 0 |
| #9 Heat ±8 clamp | 인접 턴 heat 차 `> 8` 인 구간 = 0 |
| #12 판정 공식 | `resolveBreakdown` 재계산 ↔ 저장 outcome 일치 |
| #17 Token Budget | 프롬프트 문자수 > 16,500 인 턴 (arch/100 §10.1 실측 경로) |
| #19 NATURAL 엔딩 ≥15턴 | `totalTurns < 15` 인 ALL_RESOLVED 엔딩 = 0 |
| **#41 signature 노출 금지** | 프롬프트 픽스처에 `personality.signature` 어구 등장 = 0 |
| **#42 speechStyle 어구 예시 금지** | 콘텐츠 `speechStyle` 안 따옴표 인용 = 0 |
| **#45 엔진 콘텐츠 ID 리터럴 금지** | 엔진 소스의 `NPC_`/`LOC_`/`EVT_` 리터럴 (예외 1건 허용) |
| #46 ACCRUE 프롬프트 제외 | 프롬프트 `[이번 턴 사건]` 에 `QUEST_REWARD_ACCRUE` = 0 |
| **#49 timePhase = phaseV2 미러** | `deriveTimePhaseFromV2` 재계산 ↔ 저장값 불일치 = 0 |
| #48 콘텐츠 캐시 불변 | `getEventById` 반환물 deepFreeze/딥카피 여부 (코드) |

### B. 배선 감사 (코드 ↔ 코드 ↔ DB)

`scripts/audit_payload_keys.py` (arch/100 §16 에서 이미 구현)를 흡수·확장.

- **키 불일치**: jsonb 실제 키 ↔ 코드가 읽는 키 (발견 #1·#4)
- **사문화 읽기**: 읽는데 쓰는 곳이 없는 필드 (발견 #2·#3)
- **폴백 상시 발동**: `?? 기본값` 으로 읽는 크로스 모듈 필드 중, DB 상 그 키의
  존재율이 0%인 것 — 발견 #1 의 정확한 시그니처

### C. 파이프라인 손실 (DB ↔ DB)

같은 턴의 **입력 대 출력**을 대조한다. 후처리가 조용히 콘텐츠를 지우는 부류.

- `ai_turn_logs.raw_completion` ↔ `turns.llm_output` — 대사 수·길이 (발견 #7)
- 원문에만 있고 저장본에 없는 인용문 목록 + 삭제 직전 문맥
- 확장: 프롬프트 주입 ↔ 서술 반영 (fact·아이템·NPC 등장)

### D. 도달성 (코드 상수 ↔ DB 분포)

임계·게이트 상수가 **실제 분포에서 도달 가능한가**. 발견 #5 의 형태.

- `quest-balance.config.ts` 등의 임계값을 추출
- 대응 DB 컬럼/jsonb 경로의 p50·p99·max 산출
- `임계 > p99` 이면 **사실상 도달 불가**로 신고
- 반대로 `임계 < p50` 이면 상시 발동(무의미) 신고

### E. 콘텐츠 정합 (content ↔ 코드 가정)

코드가 콘텐츠에 대해 암묵적으로 가정하는 것들을 검사. 발견 #7 의 2번째 겹.

- **별칭 충돌**: `unknownAlias` 끝 단어·`shortAlias` 가 팩 안에서 유일한가
  (수녀·안내인·장교 실측 충돌)
- 팩 계약(arch/63): `questState` 명명, `resolutionConditions`, `payload.tags`
- 프리셋 `defaultTraitId` 존재 (불변식 31)
- 에셋 참조 무결성 (초상화·장면 컷 파일 실존)

부가: **env ↔ 코드 경로**(발견 #6) — 플래그가 켜져 있는데 그 경로가 실제로
타지 않는 경우. D 족의 변형으로 흡수한다.

## 4. 루프 기전

정적 단계는 빠르고(수 분) 자유롭게 반복하되, 런 단계는 느리고(회당 ~7분)
예산이 유한하므로 **회차당 1회만** 돈다.

```
── 정적 위상 (무비용 · 자유 반복) ──────────────────
① 수집    5족 디텍터 실행 (무LLM·결정론) → 후보 목록
② 억제    baseline.json 대조 → 수용된 예외 제거
③ 검증    §7 사다리 1·2단 (정적 대조 → 과거 재생) → 증거 첨부
④ 순위    영향도(DB 빈도) × 확신도 로 정렬
⑤ 보고    상위 N건 + 증거 + 재현 명령

── 런 위상 (예산 5회 · 회차당 1번) ─────────────────
⑥ 배정    §8 규칙으로 5회를 목적별 배정. 정당화 못 쓰면 배정 금지
⑦ 계측    필요 시 로그 삽입 → build + kickstart → 런 → 회수
⑧ 수정    수정 + 회귀 테스트 추가
⑨ 재검    해당 디텍터 재실행 + 과거 재생 → 소멸 확인 → 원장 기록
```

**수렴 조건**: ①~⑤를 반복해 **연속 2회 신규 확정 0건**이면 종료
(loop-until-dry). 매 회 baseline 이 커지므로 유한하다. 런 예산이 소진되면
남은 런 필요 후보는 `deferred` 로 다음 회차에 넘긴다 — 루프는 멈추지 않는다.

**상태 파일** (커밋 대상):

| 파일 | 역할 |
|---|---|
| `scripts/selfcheck/baseline.json` | 수용된 예외 — `{id, reason, evidence, expires}` |
| `scripts/selfcheck/invariants.yaml` | 불변식 검증 질의 등록부 (A족 정본) |
| `scripts/selfcheck/ledger.jsonl` | 회차별 후보/확정/수정 수 — 추세 |

`expires` 가 핵심이다. 예외는 **영구 면제가 아니라 유예**다 — 만료되면 다시
후보로 올라와 재판정한다. 오늘 `endingResult` 처럼 "지금은 판정 불가"인 건이
런이 쌓인 뒤 자동 재검토되게 한다.

## 5. 오탐 통제 — 이 설계의 가장 어려운 부분

arch/100 §16 의 1차 감사는 후보 13건 중 실제 3건이었다. **정밀도 23%**. 이걸 그대로
두면 루프가 노이즈 생성기가 된다. 실측으로 확인된 오탐 유형과 대책:

| 오탐 유형 | 실례 | 대책 |
|---|---|---|
| **폴백 체인** | `a?.parsedType ?? a?.actionType ?? '기본'` | 표현식 내 `??` 선행 여부로 자동 분리 (구현됨) |
| **희귀 상태** | `endingResult` — RUN_ENDED 가 DB 에 1건 | **분모 동반 보고 강제**(§6) |
| **거친 정규식** | 변수명 `rs` 가 admin DB row 와 충돌 | 대상 변수명 화이트리스트 |
| **표시명 대 ID** | V8 게이트: `책임자` ≠ `마이렐 단 경` (동일 NPC) | 비교는 **npcId 로 정규화 후** |
| **의도된 예외** | 불변식 45 의 `procedural-seeds.ts` 1건 | baseline 등재 |

**철칙 — 분모 없는 판정 금지.** "0건 발견"은 "그 상태가 N번 있었는데 0건"일
때만 유효하다. N=0 이면 결론은 `판정 불가`이지 `정상`이 아니다. 오늘
`endingResult`(엔딩 런 1건)에서 이 함정을 실제로 밟았다.

## 7. 검증 사다리 — 런은 마지막 수단

같은 결론을 더 싸고 더 확실하게 얻는 순서가 있다. **위 단에서 답이 나오면
아래로 내려가지 않는다.**

| 단 | 수단 | 비용 | 결정론 | 잘하는 것 |
|---|---|---|---|---|
| 1 | **정적 대조** (코드·문서·콘텐츠·DB 질의) | 0 | ✅ | 존재/부재, 분포, 계약 위반 |
| 2 | **과거 원문 재생** | 0 | ✅ | 수정 효과의 **결정론적 입증** |
| 3 | **단기 런** (예산 5) | 75p·7분/회 | ❌ | 미영속 값 관측, 상태 강제 |

### 7.1 2단 — 과거 원문 재생 (이번 세션에서 검증된 기법)

DB 에 남은 **입력 원문**(`ai_turn_logs.raw_completion`, `turns.llm_prompt`)을
수정된 코드에 다시 통과시켜 결과를 비교한다. arch/100 §17.5 에서 대사 전멸
12턴을 이렇게 재생해 **해소 8 · 잔존 4** 를 즉시 확정했다.

```
과거 실패 턴의 raw_completion + 실제 팩 NPC 목록 → 수정된 insertMarkers
  → 귀속 마커가 초점 NPC 인가 → F-aux 삭제 대상 0 인가
```

런 대비 우위가 분명하다.

- **저빈도 결함에 유일하게 유효**하다. 전멸 패턴은 0.4/일이라 15턴 런 2회로는
  안 걸린다(실측 — 그 2런에서 `[AliasAmbiguity]` 0 발동). 재생은 12/12 를 즉시 본다.
- 결정론이라 **회귀 테스트로 승격**된다. 재생 케이스가 곧 spec 픽스처다.
- 비용 0.

**제약**: 순수 함수·결정론 경로에만 쓸 수 있다. LLM 을 다시 호출해야 하는
구간(서술 생성 자체)은 재생 불가 — 그건 3단의 몫이다.

## 8. 런 예산 5회 — 목적별 배정

런은 **정적·재생으로 못 얻는 것에만** 쓴다. 오늘 실측한 런의 능력 경계:

| 런이 잘하는 것 | 근거 |
|---|---|
| **미영속 값 관측** | `emotionalShiftHint` 는 DB 어디에도 없어 로그 계측 + 런으로만 봤다 |
| **상태 강제** | 페르소나(coercer=fear · sneaky_liar=susp · devotee=attachment)로 원하는 축을 밀어올림 |
| **고빈도 신호 전후 대조** | act 분포 TALK 100%→정상, fear 제안 5→24 (표본 27로 충분) |

| 런이 못하는 것 | 근거 |
|---|---|
| **저빈도 확정** | 1.84% → 0 입증에 연속 162턴 필요 (arch/100 §9.1) |
| **품질 판정** | 산문 좋고 나쁨은 표본 7건으로 비교 불가 (arch/100 §9.4) |
| **희귀 경로 도달** | 전멸 패턴 0.4/일 — 2런에서 0 발동 |

### 8.1 배정 규칙

```
2회  계측 런    — 미영속 값 회수. 로그 삽입 → 배포 → 페르소나 지정 실행
2회  전후 대조  — 수정 전 1 / 수정 후 1. 페르소나·턴수·시나리오 고정
1회  예비       — 재현 실패 재시도 또는 회귀 확인
```

**배정 게이트**: 후보마다 `run_justification` 을 쓰지 못하면 런을 배정하지
않는다. 다음 중 하나에 해당해야 한다.

1. 필요한 값이 **DB 에 영속되지 않는다** (계측 필요)
2. 필요한 상태가 **DB 표본에 없다** (분모 0 — §5 철칙의 해소책)
3. 대조 지표가 **런당 20건 이상** 관측된다 (통계적으로 의미 있는 표본)

3번이 arch/100 §9.4 의 교훈을 규칙으로 굳힌 것이다. "런당 몇 건 관측되나"를 먼저
추정하지 못하면 그 런은 결론을 못 낸다.

### 8.2 실행 규약

- 기본 **15턴**, 시나리오·프리셋·페르소나 명시 (`--scenario`·`--preset`·`--agent`).
  star_sand 는 `SS_*` 프리셋 필수 (graymar 기본값 `DESERTER` 는 거부됨 — 실측).
- 포인트: 15턴 = 75p. 5회 = **375p**. 잔액 부족 시 `PLAYTEST_REDEEM_CODE` 로
  자동 충전(현행 `NYDR-58AC` 500p×20회). 소진 시 어드민 `POST /v1/admin/codes`.
- 계측 로그를 넣었다면 회차 종료 시 **유지/철회를 명시 결정**한다. 유지 시
  주석에 "무엇을 관측하기 위한 것인지" 를 남긴다 (`[EmoShift]`·
  `[FocusedAuxStrip]` 이 그 선례).
- 런 결과는 게이트 통과 여부(V0~V13)와 함께 원장에 기록한다.

## 9. 비용과 실행

- 정적·재생 위상: **LLM 0 · 포인트 0 · 재시작 불필요**. 1회 수 분.
- 런 위상: 최대 **375p · ~35분 · 서버 재기동 1~2회**(계측 배포 시).
- **게이트로 쓰지 않는다.** 정밀도 23% 를 배포 차단에 걸면 해롭다.
  확정·회귀 테스트까지 붙은 항목만 개별적으로 기존 게이트(V0~V13)에 승격한다.

## 10. 이 루프가 못 잡는 것 (한계 명시)

- **서술 품질** — 산문의 좋고 나쁨. arch/100 §9.4 대로 저빈도 품질 변화는
  플레이테스트로도 안 잡힌다. 이 루프의 영역이 아니다.
- **의도 자체의 오류** — 문서·코드·DB 가 셋 다 같은 말을 하면서 함께 틀린 경우.
  교차 대조로는 원리적으로 불가.
- **런타임 경쟁 상태** — CAS 충돌, 워커 이중 처리 같은 타이밍 결함.
- **부분 검증 불변식** — "Action-First 파이프라인" 처럼 질의로 환원되지 않는 것.

## 11. 결정 필요 3건

**① 실행 방식**
(a) 온디맨드 슬래시 커맨드 `/selfcheck` 만
(b) (a) + 배포 후 자동 1회 (`launchctl kickstart` 뒤)
(c) (b) + 주 1회 크론

**② 불변식 등록 범위**
(a) 기계 검증 완전 가능한 ~25개만 (권장 — 부분 검증은 오탐 온상)
(b) 부분 포함 ~40개
(c) 50개 전부 (검증 불가는 `undecidable` 고정 표기)

**③ 수정 권한**
(a) 루프는 **보고만**, 수정은 매번 승인
(b) **저위험 범주만 자동** — 계측 로그 추가·회귀 테스트 추가·문서 정정.
    동작 변경은 승인 (권장 — 오늘 F-aux 처럼 되돌릴 수 없는 삭제 로직이 섞인다)
(c) 확정 항목 자동 수정 + 회귀 테스트 자동 생성

런 예산이 붙으면서 (b) 의 값이 올라갔다. **계측 로그 삽입은 런 위상의 전제
조건**인데(§8.1 "계측 런"), 이걸 매번 승인받으면 루프가 회차마다 멈춘다.
로그 추가는 동작 무변경·되돌리기 쉬움이라 자동화 위험이 낮다.

**④ (신규) 런 예산 회계**
(a) **회차당 5회** — 회차를 넘겨 이월하지 않음 (권장, 단순)
(b) 주당 5회 — 회차가 잦아도 총량 고정
(c) 5회를 상한으로 두되 미사용분 최대 5회까지 이월

시간·포인트 실비는 (a) 기준 회차당 375p·~35분이다.

### 인수 조건

1. **과거 결함 재현** — P1~P2 만으로 오늘 발견 #1~#4 가 후보로 잡혀야 한다.
   잡히지 않으면 디텍터가 실물을 못 보는 것이므로 설계 실패다.
2. **재생 재현** — P5 가 arch/100 §17.5 의 "전멸 12턴 → 해소 8 · 잔존 4" 를
   그대로 재산출해야 한다. 숫자가 다르면 재생 하네스가 실제 파이프라인과
   어긋난 것이다.
3. **런 절약 입증** — P6 첫 회차에서 **런 없이 확정된 건수 ≥ 런으로 확정된
   건수**. 사다리(§7)가 제 역할을 하는지의 실측 지표다.
