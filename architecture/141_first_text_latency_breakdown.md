# 141. 첫 글자 지연(7~9초) 구간 분석과 개선안

> 상태: 계측·분석 완료(2026-10-12). R1(중간 요약 사전 계산) 구현·실측 완료, R3 은 기존 동작으로 확인(§구현 1차). 계측 로그 `[TurnTiming:POST]`·`[TurnTiming:WORKER]` 는 운영에 남겨 둔다(`common/stage-timer.ts`).

## 측정 방법

- 운영 서버, GPT-6 Luna JSON 스트리밍, 정본 테스터로 그레이마르 10턴(run d2acc8dd).
- 클라이언트: 턴 제출 시각부터 첫 SSE 조각(narration/dialogue)이 도착하기까지.
- 서버: 제출 처리(POST) 구간과 워커 단계별 구간을 ms 로 기록했다. 서술 단계 안에서는 첫 토큰과 첫 조각 송출을 따로 잰다.
- 검산: 서버 구간의 합이 클라이언트가 잰 첫 표시와 턴마다 ±0.1초 안에서 맞는다(예: T6 서버 합 7.5초, 클라이언트 7.54초).

## 개선안 (기대 효과 순)

| # | 방안 | 기대 절감 | 위험·비용 |
|---|---|---|---|
| 1 | **중간 요약을 임계 경로 밖으로.** 직전 턴이 끝난 뒤(stageFollowUp) 다음 턴용 요약을 미리 계산해 노드 메모리에 캐시한다. 다음 턴은 캐시가 같은 턴 범위를 덮으면 그대로 쓰고, 아니면 LLM 없는 뼈대 요약으로 대체한다 | 평균 −0.8초, 긴 체류 −1~3.5초 | 낮음. 요약이 한 턴 늦을 수 있음 |
| 2 | **의도 해석 + 판정 분류를 한 번의 호출로.** nano 한 번이 `actionType` 과 FREE/CHECK 를 함께 낸다. JEV 확신 시 nano 생략은 유지 | −1.2~1.5초 | 중간. 두 분류기의 스펙·게이트 회귀 확인 필요 |
| 3 | **nano 타임아웃 하향(5초 → 2.5초) + 규칙 폴백.** 의도·판정·사전 결정에 적용 | 꼬리 지연 −2~3초 (T11 형) | 낮음. 폴백 비율 감시 |
| 4 | **연출 방향 nano 를 서술 호출로 흡수할지 A/B.** GPT-6 Luna 가 직접 연출을 정하게 하고, NPC 반응 결정만 남긴다(1.5초) | −0.5~0.9초 (사전 결정이 반응 nano 로만 결정됨) | 중간. 서술 품질 비교 필요 — 연출 방향은 반복 억제(불변식 50) 목적도 있음 |
| 5 | **사전 결정을 POST 와 겹치기.** 판정 결과 직후 NPC 반응·연출 방향 호출을 시작하고 워커가 그 결과를 받는다 | 최대 −2.2초 (POST 커밋과 워커 픽업 사이가 짧아 실효는 구조 변경 폭에 좌우) | 높음. 워커 lease·재시도와 결합 |
| 6 | **첫 조각을 문장보다 일찍.** 서술 조각을 쉼표·일정 글자 수에서도 내보낸다 | −0.3~0.5초 | 낮음. 클라 타이핑 연출과 조정 |
| 7 | **프롬프트 캐시 조사.** 서술 호출의 cachedTokens 가 0 이다. 고정 접두(시스템 프롬프트)가 앞에 오는지, OpenRouter 가 캐시를 전달하는지 확인한다 | 첫 토큰 −0.2~0.4초 + 비용 절감 | 낮음 |

**예상 경로:** 1·2·3 만으로 평균 약 9초 → 6.5초 안팎이 된다(꼬리 턴 개선이 큼). 4·6·7 까지 더하면 5초대가 목표다. 5 는 구조 변경이 커서 마지막에 판단한다.

## 계측 사용법

```bash
sed 's/\x1b\[[0-9;]*m//g' /tmp/graymar-server.log | grep -E "TurnTiming:(POST|WORKER)\] run=<runId>"
```

POST 줄: `prep intent routing challengeWait+resolve resultUi+memory commit total`. WORKER 줄: `queueWait firstToken firstEmit load context preDirect prompt generate postprocess+done total`. firstToken·firstEmit 은 서술 단계 시작 기준이다. 첫 표시 ≈ POST total + queueWait + load + context + preDirect + prompt + firstEmit.

## 구현 1차 — R1·R3 (2026-10-12)

### 선택지 턴 실측 (구조 대안의 전제 갱신)

같은 조건(운영 서버·GPT-6 Luna·그레이마르)에서 장소 턴을 **선택지 클릭만으로** 진행해 쟀다 (`choice_probe`, 실클라 표면 = nano 선택지 우선).

| | 직접 입력 (run d2acc8dd) | 선택지 (run c7641220, R1 전) |
|---|---|---|
| POST | 2.7~7.2초 (의도 nano + 판정 nano) | **13~29ms** (이벤트 선택 JEV 턴 0.4초) |
| 첫 조각 | 6.8~14.2초 | **3.2~3.6초**, 장소 5턴째부터 5.6~7.1초 |

선택지 턴은 의도·판정이 규칙으로 끝나 POST 가 즉시 돌아온다. **9초 문제는 직접 입력 턴(35%)의 문제**이고, 선택지 턴(65%)의 지연은 워커 안(중간 요약·사전 결정·첫 조각)에만 있다.

### R1 — 중간 요약을 지난 턴에 미리

- `MidSummaryService` 의 경량 LLM 압축을 **압축 원문 해시로 캐시**한다(진행 중 Promise 공유, 실패는 캐시하지 않음, 300건 상한).
- `ContextBuilder` 가 이번 턴 컨텍스트를 만들 때, 다음 턴의 초기 턴 묶음(이번 세션에서 마지막 3턴을 뺀 것 — 모두 서술 확정 턴)을 `prewarm` 으로 미리 압축한다. 결과를 기다리지 않는다. 예측이 빗나가면 다음 턴이 평소처럼 직접 계산한다.
- 압축 원문은 서술 300자×최대 1500자라, 초기 턴이 5개를 넘으면 원문이 고정돼 그 뒤로는 캐시만 쓴다(종전에는 같은 원문을 매 턴 다시 압축했다).
- 실측 (run bab64df8, 선택지 12턴): 중간 요약이 걸리는 턴 7~12의 context **1.08~1.37초 → 11~22ms**. 압축 호출 자체는 직전 턴 처리 중에 1.1~1.5초 걸려 끝나 있었다(`llm_call_logs` stage `mid-summary` 가 한 턴 앞에 기록됨). 스펙 5건 추가, 전체 3,223 passed.

### R3 — 결과 먼저: 이미 동작 중

클라이언트 확인 결과 R3 의 골자는 이미 있다.
- 제출 즉시 플레이어 행 + 서술 로딩 셸(2026-08-06 `makeSubmitPendingNarrator`).
- POST 응답 시점에 판정 메시지(주사위 애니메이션·결과 배너, FREE 는 "일상 행동 — 판정 불필요")를 서술보다 먼저 붙인다(`processTurnResponse` immediateMsgs).
- 선택지 턴은 POST 가 수십 ms 라 배너가 사실상 즉시 뜬다. 직접 입력 턴은 판정 결과가 POST 안의 nano 2회 뒤에 나오므로 배너도 3~7초에 뜬다 — 이건 연출이 아니라 의도·판정 분류 단축(개선안 2·3)의 문제다.

따라서 R3 으로 추가 구현한 것은 없다.
